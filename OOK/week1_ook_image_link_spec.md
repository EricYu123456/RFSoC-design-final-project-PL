# 第一週原型規格：使用 OOK 與重傳，正確傳送一張灰階圖片

版本：v0.2  
日期：2026-11-03  
負責組別：PL 組

## 1. 這週要完成什麼？

用 Vivado 2024.2 的 XSim 模擬器，完成一張圖片的傳送與接收。圖片資料與接收確認訊息 ACK，都要經過 OOK 調變與解調。

**成功條件：接收端收齊全部圖片資料，而且重建圖片的每一個 byte 都與原圖相同。**

| 項目 | 本週規格 |
| --- | --- |
| 後續硬體目標 | RFSoC 4×2 |
| 本週執行方式 | 純模擬，使用 Vivado / XSim |
| 主要開發方式 | 可綜合的 Verilog RTL，搭配現成 Vivado IP |
| 圖片 | 單張 640×480、8-bit 灰階圖片，無壓縮 |
| 調變 | 圖片與 ACK 都使用 OOK |
| 錯誤處理 | CRC 檢錯，加上 ARQ 重傳 |
| 傳送方式 | 一次傳一包，收到 ACK 才傳下一包 |

8-bit 灰階代表每個像素有 256 種亮度，用 1 byte 表示。這裡的「黑白圖片」是灰階圖片，不是只有黑、白兩種值的 1-bit 圖片。

本週先完成單張圖片的收發；影片、多跳轉送、FEC，以及與 PS 組、rubikPI 組的介面整合，留到後續階段。這次的模擬也不包含實際 RFDC、DAC、ADC、板上時脈設定或類比線材特性。

## 2. 先認識幾個名詞

| 名詞 | 白話說明 |
| --- | --- |
| OOK | 用「有載波」表示 1，「沒有載波」表示 0 |
| 封包 | 把大張圖片切成很多小份，每份附上編號與檢查碼 |
| CRC | 用來檢查資料是否出錯的檢查碼，本身不會修正錯誤 |
| ACK | 接收端回覆的「這一包已正確收到」訊息 |
| ARQ | 沒有收到有效 ACK 時，再傳一次同一包 |
| Stop-and-Wait | 停等式傳輸：傳一包、等確認、再傳下一包 |
| 半雙工 | 兩端輪流發送，同一時間只有一端發送 |
| Testbench | 模擬用的測試環境，負責餵資料、製造錯誤與檢查結果 |

## 3. 整體收發流程

模擬中分成兩個邏輯角色：A 是圖片發送端，B 是圖片接收端。這是測試環境中的角色劃分，不代表本週要使用兩塊實體板卡。

```text
圖片方向：A → B

圖片 bytes → 分包、加 CRC → OOK 調變
    → 理想通道 → OOK 解調 → 檢查 CRC → 保存圖片資料

確認方向：B → A

產生 ACK、加 CRC → OOK 調變
    → 理想通道 → OOK 解調 → 檢查 ACK → 決定下一步
```

正常情況如下：

```text
A：送第 0 包 ────────────→ B：檢查、保存第 0 包
A：等待 ACK ←──────────── B：用 OOK 回 ACK 0
A：送第 1 包 ────────────→ B：檢查、保存第 1 包
A：等待 ACK ←──────────── B：用 OOK 回 ACK 1
……直到第 299 包收到確認。
```

**ACK 必須真的走過反向 OOK 收發鏈路。** A 只能根據解調、解析、CRC 檢查後的 ACK 決定是否成功；B 不能直接拉一條「收到成功」的控制線給 A。

模擬使用兩條有方向的 sample 通道，分別代表 A→B、B→A，並限制兩端輪流發送。輪到另一端之前，先保留一小段安靜時間。

### 圖片一開始怎麼送進來？

Python 先將照片轉成 640×480 灰階像素，輸出 assets/image.mem。每行是兩個十六進位字元，代表一個像素，例如 00 是黑色、FF 是白色。

Testbench 使用 $readmemh() 載入這 307,200 個 bytes，再透過 data[7:0]、valid、ready 介面，逐 byte 餵給 TX。只有 valid 與 ready 同時為 1，才前進到下一個像素。

TX 先把一包 1,024 bytes 存進 BRAM，再進行 OOK 傳送。收到有效 ACK 後才接收下一包；需要重傳時，重讀已保留的 BRAM，不再向 testbench 要新的圖片資料。

完整圖片在 testbench 的記憶體中；本週的 RTL 不需要先存下整張圖片，也不需要 PS 程式參與。

## 4. OOK 怎麼做？

### 發送端

DDS Compiler IP 持續產生正弦載波，Verilog 依照要送的 bit 選擇輸出：

```text
bit = 1：輸出正弦載波
bit = 0：輸出 0
空閒時：輸出 0
```

每個 bit 都占固定時間。即使 bit 是 0，也必須送滿該 bit 的零樣本，不能把它省略。

### 接收端

用 Multiplier IP 將接收樣本平方，再把一個 bit 時間內的結果加起來，得到能量 E：

```text
E = 這個 bit 內，所有「接收樣本 × 接收樣本」的總和

E 大於門檻：判成 1
E 小於或等於門檻：判成 0
```

第一版先量出理想「1」的能量 E1，把固定門檻設成 E1 的一半。這個門檻先作為參數設定，不做自動增益或門檻調整。

### 暫定參數

| 項目 | 數值 | 說明 |
| --- | --- | --- |
| 取樣時脈 | 100 MHz | 每 10 ns 處理一個樣本 |
| 載波頻率 | 12.5 MHz | 一個載波週期有 8 個樣本 |
| 每個 bit 的樣本數 | 16 | 一個 bit 包含 2 個載波週期 |
| 原始 bit rate | 6.25 Mbit/s | 尚未扣掉封包、ACK 與等待時間 |
| 波形樣本格式 | 16-bit signed | 正弦波會有正、負值 |
| 平方結果 | 32-bit | 保留完整乘積 |
| 能量累加器 | 36-bit | 預留累加 16 個樣本的空間 |

圖片與 ACK 使用相同的 OOK 參數。這些數值是模擬用的起始設定，尚未對應 RFSoC 的實際 RFDC 設定。

### 本週的同步與通道假設

- 兩端共用模擬時脈，已知每個 bit 的時間邊界。
- 發送端只在 bit 邊界開始送資料；接收端每 16 個有效樣本做一次判決。
- 通道先採固定增益 1、無雜訊、無頻率偏移、無額外傳播延遲。
- DDS 與 Multiplier 的管線延遲要確實對齊資料、有效訊號與計數器。
- 接收端仍須自行搜尋封包的 Sync word；共同時間基準不會直接提供封包起點、編號或內容。

這樣可以先驗證 OOK、封包與重傳流程。未知的 bit 邊界、雜訊與增益變化，後續再加入。

## 5. 圖片怎麼切成封包？

一張圖片共有：

```text
640 × 480 × 1 byte = 307,200 bytes
307,200 ÷ 1,024 = 300 包
```

圖片採逐列排列：先傳最上面一列，由左到右，再傳下一列。傳輸內容只包含像素 bytes，不包含 PNG、JPEG 或 BMP 的檔案標頭。

| 項目 | 規格 |
| --- | --- |
| 每包圖片資料 | 固定 1,024 bytes |
| 每張封包數 | 固定 300 包 |
| 封包編號 packet_id | 0～299 |
| 圖片編號 frame_id | 單張測試先用 0；同一次模擬傳下一張時再增加 |
| 第 k 包在原圖中的位置 | 從第 k × 1,024 個 byte 開始 |

每次重傳沿用相同的 frame_id、packet_id 與資料內容。

## 6. 封包格式

以下數值是本專案自行訂定的格式。

### 圖片資料封包：共 1,038 bytes

| 順序 | 欄位 | 大小 | 用途 |
| --- | --- | --- | --- |
| 1 | Sync word | 4 bytes | 固定為 0xD391C5A7，讓 B 找到資料封包起點 |
| 2 | frame_id | 2 bytes | 這是哪一張圖片 |
| 3 | packet_id | 2 bytes | 這是圖片中的第幾包 |
| 4 | payload_len | 2 bytes | 固定為 1,024，也就是 0x0400 |
| 5 | Payload | 1,024 bytes | 真正的圖片資料 |
| 6 | CRC-32 | 4 bytes | 檢查上述三個 Header 欄位與 Payload |

Header 就是 frame_id、packet_id、payload_len，合計 6 bytes。Sync word 不納入 CRC。

本週是固定長度協定：找到 Sync word 後，一律按照固定位置接收 6-byte Header、1,024-byte Payload、4-byte CRC。即使 payload_len 被傳錯，也不能拿錯誤長度決定封包結尾。

### ACK 封包：共 12 bytes

| 順序 | 欄位 | 大小 | 用途 |
| --- | --- | --- | --- |
| 1 | Sync word | 4 bytes | 固定為 0xAC4B7E29，讓 A 找到 ACK 起點 |
| 2 | frame_id | 2 bytes | 確認哪一張圖片 |
| 3 | packet_id | 2 bytes | 確認哪一包已保存 |
| 4 | CRC-32 | 4 bytes | 檢查 ACK 的 frame_id 與 packet_id |

ACK 的 Sync word 也不納入 CRC。本週只使用 ACK；資料出錯時由逾時機制觸發重傳。

### 傳送順序統一規則

- 所有多 byte 欄位，包括 CRC，都先傳高位 byte，再傳低位 byte。
- 每個 byte 先傳 bit 7，最後傳 bit 0。
- 例如 frame_id = 0x1234，就先傳 0x12，再傳 0x34。
- 解析封包內容期間，不把 Payload 裡恰好相同的 Sync word 誤認為另一包起點。

## 7. CRC 的規格

資料與 ACK 都採 CRC-32/ISO-HDLC。兩邊必須使用完全相同的設定。

| 參數 | 數值 |
| --- | --- |
| Poly | 0x04C11DB7 |
| Init | 0xFFFFFFFF |
| RefIn / RefOut | true / true |
| XorOut | 0xFFFFFFFF |
| 標準測試 | ASCII 字串 123456789 的結果應為 0xCBF43926 |

如果 RTL 採向右位移的寫法，使用反射後的多項式 0xEDB88320。這只是實作形式不同，最後結果必須相同。CRC 內部的反射設定，與前一節規定的通道傳送順序是兩件事。

每個封包各自重新初始化 CRC；Python 使用 zlib.crc32() 產生獨立參考結果，避免 TX、RX 用了相同的錯誤算法卻互相通過。

## 8. 重傳規則

### A：圖片發送端

1. 先準備好目前這一包的完整內容，再開始 OOK 發送，避免封包中途缺資料；保留資料直到收到有效 ACK。
2. 用 OOK 傳完資料封包，切換成等待 ACK。
3. 接收反向 OOK 波形，解調並解析 ACK。
4. ACK 的 CRC 正確，而且 frame_id、packet_id 都符合目前等待的封包，才算確認成功。
5. 收到有效 ACK 後，清除重試次數，準備下一包。
6. 若等待逾時，重傳同一包。
7. 第 299 包也收到有效 ACK 後，A 才宣告這張圖片傳送完成。

CRC 錯誤、編號不符或來自其他圖片的 ACK，都不算成功，也不重新延長等待時間。

### B：圖片接收端

1. 搜尋資料 Sync word，收滿固定長度封包。
2. 先將資料放在一包大小的暫存區，檢查 CRC、frame_id、packet_id 與 payload_len。
3. CRC 或欄位檢查失敗：丟棄該包，不回 ACK。
4. 新的有效封包：將資料交給圖片儲存端；確定保存完成後，才用 OOK 回 ACK。
5. 已保存過的有效封包：再次回 ACK，避免 ACK 遺失導致流程卡住；不重複增加收包數。

本週的圖片儲存端由 testbench 模擬，負責依編號把資料放回完整圖片。RTL 保留一包的暫存即可，完整影像不用先放進 PL 記憶體。testbench 確認保存完成的訊號只給 B 本地使用，A 仍須等待反向 OOK 的 ACK。

B 收齊 300 包後仍保持接收能力，因為最後一包的 ACK 也可能遺失，A 可能再次傳送第 299 包。

### 時間與重試設定

| 參數 | 起始設定 | 意義 |
| --- | --- | --- |
| 方向切換的安靜時間 | 至少 64 個 sample clock | 發送結束後，讓兩端輪流接手 |
| ACK 等待逾時 | 4,096 個 sample clock，約 40.96 μs | 從 A 送完資料封包的最後一個樣本開始計時 |
| 最大重傳次數 | 10 次 | 加上第一次發送，一包最多嘗試 11 次 |

12-byte ACK 本身需要 1,536 個 sample clock。4,096 拍的等待時間還要容納接收管線、CRC 檢查、資料保存與方向切換，因此整合時必須驗證最慢回覆時間確實小於此值；若超過，就增加逾時參數。

A 收到 ACK 後，也要等 B 發送結束並滿足安靜時間，才開始下一包。測試環境要檢查兩端不會同時發送。若最後一次嘗試仍然逾時，回報傳輸失敗，不能把不完整圖片當成成功。

## 9. 哪些用 IP？哪些自己寫？

| 功能 | 實作方式 | 大約需要做的事 |
| --- | --- | --- |
| 載波產生 | DDS Compiler IP | 設定固定頻率、單通道、16-bit 正弦輸出 |
| OOK 開關 | Verilog | 依照 bit 選擇載波或 0 |
| 樣本平方 | Multiplier IP | 16-bit signed × 16-bit signed，保留 32-bit 乘積 |
| 能量累加與判決 | Verilog | 每 16 個樣本累加一次，再與門檻比較 |
| 一包資料的暫存 | Block Memory Generator IP | 保留 TX 待確認資料，以及 RX 待檢查資料 |
| 封包組裝與解析 | Verilog | 處理 Sync word、Header 與固定資料長度 |
| CRC-32 | Verilog | 做成可共用的模組，資料與 ACK 各自使用 |
| Stop-and-Wait 控制 | Verilog 狀態機 | 等待 ACK、計時、重傳、檢查重複封包 |
| 圖片轉換與結果比對 | Python + testbench | 產生測試資料、重建圖片與逐 byte 比對 |

正向與反向可重複使用相同的 OOK TX、OOK RX、CRC 模組設計。CRC、封包與控制邏輯本身很小，先直接寫 Verilog，方便看懂與除錯。

資料 byte 介面先自行訂為 data[7:0]、valid、ready，只有 valid 與 ready 同時為 1 時才前進。sample 波形端則固定每拍一個樣本，不能因為 byte 端等待而拉長或縮短某個 bit。

## 10. 怎麼驗證「圖片 100% 正確」？

最終 PASS 必須同時滿足：

1. B 收到同一張圖片的 300 個不同封包，編號 0～299 全部齊全。
2. 每包都是 CRC 與欄位檢查通過後，才交給儲存端。
3. A 收到全部封包的有效 ACK。
4. 重建圖片的 307,200 個 bytes，逐一與原圖比較，差異數為 0。

CRC 仍有漏檢可能，因此不能只用「CRC 全過」代表圖片完全正確。本週用原圖逐 byte 比對，作為模擬的最終驗收。原圖比對只負責判定測試結果，不會偷偷提供正確資料給接收端或幫忙決定重傳。

### 必須通過的測試

| 測試 | 如何製造情況 | 預期結果 |
| --- | --- | --- |
| 正常傳送 | 理想通道，不注入錯誤 | 300 包收齊，圖片完全一致，不發生重傳 |
| 圖片資料錯誤 | 第一次傳某包時，在 CRC 產生後、OOK 調變前反轉一個 Payload bit | B 檢出 CRC 錯誤；A 逾時重傳，最後圖片一致 |
| ACK 損壞 | 第一次回某個 ACK 時，在 CRC 產生後、OOK 調變前反轉一個編號 bit | A 忽略壞 ACK；重傳資料後完成確認 |
| ACK 遺失 | 將某一次完整 ACK 的通道波形設為 0 | A 逾時重傳；B 不重複計數，重新用 OOK 回 ACK |
| 最後一包 ACK 遺失 | 第一次 ACK 299 的波形設為 0 | B 持續接收並再次回 ACK，整張傳輸最後完成 |
| 持續出錯 | 每次都破壞同一包 | 達重試上限後回報失敗，不宣告 PASS |
| ACK 編號不符 | 送一個 CRC 正確、但 packet_id 不符的 OOK ACK | A 不把它當作目前封包的確認 |

這些 bit 反轉是可重現的數位錯誤注入，用來驗證 CRC 與重傳；本週先不把它當成類比雜訊模型。

測試環境另外設定總時間上限，避免程式出錯時模擬無限執行。

### 除了延遲，還會輸出什麼？

| 結果 | 如何閱讀 |
| --- | --- |
| 原圖、接收圖、差異圖 | 檢查圖片內容；完全一致時，差異圖全黑、bytes 差異數為 0 |
| 資料與 ACK 的 OOK 波形 | 查看 bit 開關、正弦載波、接收能量與判決門檻 |
| 不同封包接收數 | 應從 0 增加到 300，重複包不增加 |
| CRC 錯誤、重傳、逾時與重複包數 | 確認錯誤發生後，系統如何恢復 |
| 事件紀錄 | 記下每個資料包與 ACK 何時發送、檢查、保存或逾時 |
| 有效吞吐率 | 成功圖片的 307,200 × 8 bits，除以第一包開始到最後 ACK 被確認的時間 |

完整圖片成功時，Python 會再獨立比對一次像素，並記錄原始像素與接收像素的 SHA-256。有效吞吐率的分子不包含 Header、CRC、ACK 或重複傳送的資料。

本週不以這些理想通道測試推論實際 RF 的 BER–SNR 表現。資源使用量則需要另跑合成，而且需要有效的 ZU48DR 合成授權。

## 11. 建議完成順序

以下以五個工作天安排；可分成「OOK 與 IP」、「封包、CRC 與重傳」、「testbench 與圖片驗證」三條工作。

| 階段 | 工作 | 驗收結果 |
| --- | --- | --- |
| 第 1 天 | 建立 DDS、OOK TX、OOK RX | 短 bit 序列可正確收回 |
| 第 2 天 | byte / bit 轉換、CRC、資料與 ACK 格式 | 正反兩方向的短封包都能通過 OOK 與 CRC 檢查 |
| 第 3 天 | 加入停等控制、逾時、重傳與重複封包處理 | 單包遇到資料或 ACK 錯誤仍可完成 |
| 第 4 天 | 串接 300 包圖片傳輸與重建 | 整張圖片逐 byte 一致 |
| 第 5 天 | 跑完整測試、檢查 RTL 可綜合性、整理展示 | 測試紀錄、圖片與關鍵波形齊全 |

完整圖片的正向 OOK 波形約需四千萬個 sample clock，反向 ACK 與等待時間還會再增加。這是模擬中的時脈數，不是電腦執行秒數。先用短序列、單包除錯，再跑完整圖片；全圖測試只記錄必要波形，避免檔案過大。

## 12. 本週應交付的成果

- 一份可重建的 Vivado 專案或 Tcl 建立腳本，以及 IP 設定。
- OOK 收發、CRC、封包與重傳控制的 Verilog 原始碼。
- testbench，以及圖片輸入、重建、比對用的 Python 程式。
- 一張原圖、一張正確接收的圖片，以及 bytes 差異數為 0 的測試紀錄。
